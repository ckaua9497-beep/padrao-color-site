@AGENTS.md

## What this is

Online store for Padrão Color (print shop): every product has a configurable procedural 3D mockup. Stack: Next.js 16 App Router, React 19 + React Compiler, Tailwind 4, three.js + React Three Fiber + drei, strict TypeScript. UI copy and code comments are Brazilian Portuguese; keep them that way.

`README.md` is the detailed reference: catalog fields, m²/express/size-grid pricing, how to add a mockup kind, and design-system rules. Read it before touching those areas. Sibling folders in the parent directory:
- `../padrao-loja`: frozen JS prototype. Reference only; never edit it.
- `../alteraçoes`: the client's task checklist and the API PDF (`DocumentacaoPadraoColor.pdf`).

## Commands

- `npm run dev -- -p 3100`: dev server. Port 3100 is what `../.claude/launch.json` ("site") starts and the preview tools expect. `next dev` writes to `.next/dev`, so `npm run build` can run alongside it. `scripts/dev.mjs` first starts the local multiloja PostgreSQL (embedded, `.data/postgres`, port 5433) unless `DATABASE_URL` is set or the port is already open; `npm run db` starts only the database.
- `npm run build`: production build. Product, category and kit pages are SSG.
- `npm run lint`: the bar is 0 errors and 0 warnings, including the React Compiler rules.
- `npx tsc --noEmit`: type check (there is no script for it).
- `npm test`: runs `node --test` over `src/**/*.test.ts`.
  - Single file: `node --test --disable-warning=MODULE_TYPELESS_PACKAGE_JSON src/lib/pricing.test.ts`.
  - Add `--test-name-pattern="..."` to filter by test name.
- `npm run sync:catalog`: pulls the catalog and storefront from the API into `src/data/`. It is GET-only, takes about 60 s and needs `.env.local` (see `.env.example`). Run `npm test` afterwards: the per-kind count snapshot in `src/lib/mockup.test.ts` flags products that changed mockup kind. A group whose `GET /produtos?id_grupo=` brings no valid variation (rows without a numeric `id`, such as group 532's `[{"ERRO":"Bad Response"}]` on 2026-10-23) is left out of the catalog with a warning. When the API merges groups into another, map the old IDs in `GRUPOS_JUNTADOS` (`src/lib/catalog.ts`) so old product links redirect.
- `npm run sync:novos`: consumes the site's own API (`/api/novos`, same format as the Padrão API) and writes `src/data/catalog-novos.json`, which `catalog.ts` merges with `catalog.json` only when `PRODUTOS_NOVOS_NO_SITE` is on (off since 2026-10-25: the site shows only Padrão API products; internal QA pages read them through `getQaProducts`). Needs the dev server up (or `-- --local`). Source of truth: `src/data/novos/fonte.json`. README "Produtos novos".
- `npm run fotos:novos`: renders each new product's 3D mockup with the brand pattern (`/design-system/fotos`) and saves 1200×1200 transparent WebP photos to `public/produtos-novos/` (`-- --tam=600` for another size; rendered at device scale 3, then reduced). Needs Chrome and the dev server.
- `npm run shots -- --p=<id or slug>[,…] [--giros=0,35,-35,90,180] [--op="Key:Value;…"] [--faces=back,<surface id>,…] [--face=<surface id>] [--saida=dir]`: photographs a product's 3D mockup from several angles (the `/design-system/fotos` page in headless Chrome, shared driver `scripts/lib/chrome-cdp.mjs`) plus a contact sheet `folha.webp` (default output `<tmp>/padrao-shots/<slug>/`). `--faces` gives the back and the listed extra surfaces their own brand art (other colours); `--face` sets the surface "being edited". Every 3D change is checked this way against the real product photos before committing; the photos from Padrão's review are in `../alteraçoes/observacoes-site-novo/ref/` (reference only, never publish). Needs the dev server.
- `npm run sync:templates`: reads every product's official print template (gabarito) into `src/data/templates.json` (README "Gabaritos"). Run it after `sync:catalog`. The first run downloads ~5 GB into `.cache/gabaritos/` and takes several minutes; later runs reuse the cache. `src/lib/templates-data.test.ts` then flags options that lost their template sheet.

**Test-module import rule.** Tests run on raw `.ts` through Node's type stripping, with no bundler. Any module a test imports, directly or transitively, must:
- import runtime values through relative paths with an explicit `.ts` extension, never through the `@/` alias;
- bring in types only with `import type`;
- contain no JSX.

Examples: `src/lib/{mockup,pricing,orders,party,facade}.ts`, `src/components/mockup/environments/*.ts` and `src/components/mockup/models/apparel/{body,garment,pieces}.ts`.

## Architecture

### Data flow

The Padrão Color API (`PADRAO_API_URL`; the lab host answers only over HTTPS) is read at build time:
1. `scripts/sync-catalog.mjs` writes `src/data/{catalog,storefront,business-types,finishes}.json`.
2. `src/lib/catalog.ts` exposes that data.
3. Pages are generated from it. Product = API group; variation = API product, whose ID goes into the order.

**Live catalog** (`PADRAO_CATALOGO_VIVO=true`, never during `next build`; README "Catálogo em tempo real").
- `src/lib/catalogo-vivo.ts` reads `GET /grupos` (active groups and group fields) and `GET /produtos?id_grupo=` (variations, built with the same `mapGroup`), with in-memory caches and `catalog.json` as the fallback.
- `catalog.ts` exports `catalogView(file)`. The sync exports stay synchronous; `await catalogoVivo()` returns the same functions over the live data.
- New pages or routes that show or price products must use `catalogoVivo()` (listings, menu, search index) or `produtoDoGrupo()`/`produtoDaPagina()` (product page, cart, order), and the page needs `revalidate = 600`.
- Pure rules live in `src/lib/catalogo-grupos.ts`. Local simulator: `scripts/padrao-mock.mjs` (port 3194, use `127.0.0.1`).

At runtime, only account, order, price and template routes call the API:
- They live in `src/app/api/*` and use `src/lib/api/client.ts` and `padrao.ts`. Both are `server-only`, so the integration token and customer tokens never reach the browser.
- The API host does not send the Let's Encrypt intermediate certificate, so Node's `fetch` rejects it (`UNABLE_TO_VERIFY_LEAF_SIGNATURE`) and every call (login, signup, prices, orders) fails. The transport in `src/lib/api/transport.ts` (used by `client.ts` and `sync-catalog.mjs`) therefore uses `node:https` with the chain in `src/lib/api/tls-chain.ts`. `tls-chain.test.ts` fails 60 days before those certificates expire; refresh them from `http://<name>.i.lencr.org/`.
- The API's firewall blocks by IP whoever opens too many connections or fails too many logins (it happened on 2026-10-07; hosts outside Brazil can't connect at all). So `client.ts` allows at most 6 GETs in flight per process. When the host is unreachable it fails every call with `ApiError` 503 for 30 s, without opening sockets, and `sync:catalog` stops at the first unreachable error. `transport.ts` gives `timeoutMs` to the connection (TCP + TLS), then uses it as the time allowed with no bytes, and retries a dead keep-alive socket once on a fresh connection (GET and login only). `transport.test.ts` covers this with local servers only. Never test the network layer or wrong-password logins against the real API.
- Server logs: `[api] METHOD /path: sem conexão com HOST (...)` means the host is down or blocking this IP; `sem resposta da API por N s` means it connected but stopped responding; other non-business HTTP statuses (5xx, 403, 429, 3xx) are logged with their status.
- The logged-in session is a sealed cookie (`src/lib/session.ts`, `src/lib/api/seal.ts`).
- POST routes go through `src/lib/api/guard.ts`, which checks the origin and applies the rate limit.
- Reseller prices: `src/lib/customer.tsx` (client store) fetches `/api/precos`, which calls `GET /produtos` with the customer's own token. Cart lines and `precoTotal` use those prices. The "a partir de" of product cards, the category banner and the header search comes from `/api/precos/minimos` (`useFromPrices`, one batched call per render; catalog price for everyone else).
- Customization is per variation (`src/lib/customizacao.ts`, pure and tested): `Product.customizacoes` holds the distinct profiles (art mode, accepted attachment types, art-creation price, web2print) and `Variation.cz` the index, built by `src/lib/catalog-map.ts` with the site's rules on top of the API's `customizacao`/`tipos_anexo`. Read it with `customizacaoDa(product, variation)`: "nenhuma" and "neon-modelo" take no art and send no attachments; extra attachment types become optional "Arquivos complementares" on the product page (cart/order `kind: "extra"` + `tipo`).
- Checkout builds the `gerarpedido` payload in `src/lib/orders.ts`, in the format of the order example Padrão sent (products with `id`, `groupId`, `variations`, `price`, `precoTotal`, `package`, `tipoProducao`, `productionTime`, `arte {tipo, preco, anexos}`…; envelope with `data`, `hora`, `previsao`, `entrega`, `frete`); open assumptions are listed in the file header. Catalog data per line (image, category, packaging, attachment types) comes from `productFacts` (`src/lib/order-facts.ts`). A real POST is sent only when `PADRAO_ORDERS_ENABLED=true`; otherwise the payload is simulated and shown.
- Art files go to Bunny Storage at checkout: the cart keeps them in IndexedDB (`printFile` + `artFiles`, `print-store.ts`), `components/cart/art-upload.ts` posts each one to `/api/arte`, which PUTs to Bunny with the server-only `BUNNY_ACCESS_KEY` (`src/lib/bunny.ts`; names and URL checks in the pure `src/lib/art-files.ts`), and the public URLs go in `produtos[].arte.anexos`. The order route only accepts URLs from the configured public folder or from the site's own stored-file folder (below). Without Bunny env vars, or with Bunny down, `/api/arte` stores the file in the database instead. Local simulator: `scripts/bunny-mock.mjs`. Never put the real AccessKey in tracked files or logs.
- **Order queue** (`src/lib/fila-pedidos/`, README "Fila de pedidos do site"): when the order can't reach `gerarpedido` the site keeps it instead of failing.
  - `processar.ts` holds the order close shared by `/api/pedidos` and the queue (`prepararPedido`: GET /cliente, prices, art/terms/price checks, payload; `enviarPedido`: the POST). Pure rules in `regras.ts` (tested): `classificarFalha` → "sem-conexao" (nothing left: retry), "recusado" (4xx: customer fixes, or staff), "incerto" (may have been created: staff checks first, never auto-retried).
  - Table `pedidos_fila` (migration 5, `repo.ts`): validated order JSON, payload when built, customer token sealed with a key derived from `PADRAO_SESSION_SECRET`, attempts, history. The checkout answers 202 `{mode: "queued", protocolo}` and clears the cart; "Meus pedidos" lists the customer's entries.
  - Art files Bunny didn't take live in `arquivos` (owner `fila/<cliente>`) and are served by `/api/pedidos/arquivo/<nome>` (always as a download); the public URL uses `MULTILOJA_URL_PUBLICA` (request origin in dev). Before a resend, the queue uploads them to Bunny when it is back.
  - `worker.ts` starts from `src/instrumentation.ts`: one pass per minute, up to 3 entries, stops at the first offline error and respects the client circuit breaker; backoff 1→60 min, 72 attempts, then "conferir". `FILA_PEDIDOS_DESLIGADA=true` turns it off. Staff handle entries in `/admin/fila-pedidos` (send now, mark as sent with the order number, back to auto-resend, cancel).
- **Business days and holidays** (`src/lib/dias-uteis.ts`, pure and tested; `src/lib/feriados.ts`, server-only): a business day is Mon–Fri outside the dates of `GET /feriados` (holidays plus any other day Padrão registers), cached 6 h, with national holidays as the fallback. The production day ends at 18:00 Brasília: an order or art that arrives later, or on a non-business day, counts from the next business day (`inicioDaContagem`). `buildOrderPayload` takes `holidays` (both callers pass `await feriados()`); "Meus pedidos" warns that art resent outside business hours pushes the forecast 1 business day (`previsaoAposReenvio`).
- **Customer cancellation** (`src/lib/cancelamento.ts`, pure and tested): within 15 min of the purchase (`GET /pedidos` `data` + `hora`, Brasília) the customer cancels the whole purchase (`/cancelarcompra`) or one item (`/cancelarpedido`, its own button only when 2+ items are still cancellable); both routes re-check the window on the server through `compraRecente` (`src/lib/api/compras.ts`). Refund follows what was paid: each item's share of `credito_usado` (back to the account balance automatically) and of `valor_pago` (refunded by Padrão). Multiloja purchases are never cancelled there.
- **Customer data** (`src/lib/cliente.ts`, pure and tested; format checked against a real `GET /cliente` of 2026-10-26): balance in `conta_corrente.credito` (old `saldo` still read: `saldoDaConta`), `email` may be empty with the address only in `email_cadastro` (`emailDoCliente`), `nascimento` in DD/MM/AAAA. Delivery route: the route name is its colour ("VERDE", dot colour mapped from the name) and `taxa_rota` comes on the delivery address; no route = "Transportadora" (no route delivery). With a route, the fee goes in the order as freight unless payment on pickup is allowed (assumed `pagamento_antecipado` "N"). "Minha conta" shows it; the checkout charges it as the Delivery Padrão freight.
- **Checkout delivery and payment** (`src/lib/entrega.ts`, pure and tested; UI `components/cart/EntregaCheckout.tsx`), like Padrão's old site: "Delivery Padrão" (the registration's delivery address, always by its route; route fee as freight unless pay-on-pickup), "Retirada em uma das lojas Padrão Color" ("Selecione uma loja", two-column cards in the old checkout's order, names and addresses, Loja São João preselected; `LOJAS_RETIRADA`: 5 own stores + 2 partner points, Niterói and Serra-ES, ids from the official site pending Padrão's; never freight; partners never take pay-on-pickup) and "Frete por transportadora" (registration or other address; cart quoted by `POST /api/pedidos/frete` → `src/lib/frete-pedido.ts`; no API key or an item without packaging = freight agreed later). Payment: Pix, card and "Pagar na retirada" only where `pagaNaRetiradaPermitido`; no boleto anywhere (multiloja hides it with `FORMAS_FORA`). `prepararPedido` re-quotes the carrier, builds `entrega`/`frete` with `orderDelivery` (returns the refusal text) and `paymentProblem`, and compares the total including freight; `precoTotal` and `pagamento.valor` include `frete`.
- **WhatsApp:** `STORE.whatsapp` is (21) 97246-3737; `STORE.whatsappTratamento` (`#PROBLEMANOPEDIDO`) is the file-treatment team, the "Falar com o tratamento" button on every non-cancelled item in "Meus pedidos".
- **Sent arts** (`src/lib/artes-enviadas/`, rules pure and tested in `regras.ts`, DB in `repo.ts`): "Meus pedidos" shows per item the art on the template (`CartItem.previa`, a JPEG from `buildGabaritoPreview` made at add-to-cart next to the print PDF; uploaded at checkout as `OrderItemInput.previa`, never in `arte.anexos`), what the customer sent (checkout files and art resends), what Padrão received (`produto.arquivos`) and the art state (`estadoDaArte`). Table `artes_pedido` (migration 6): `/api/pedidos` saves the created order (compra) or the queued one (protocolo, number joined from `pedidos_fila`); `/api/pedidos/[id]/arte` saves resends. Saving never fails the order; API items match saved ones by variation, then position (`casarItens`).
- **Art terms** (`src/lib/termos-arte.ts`, tested): every personalized product asks for "Li e aceito os termos de envio de arte" in `ArtStep` (`TermosArte.tsx`) before add-to-cart; the cart line keeps `termosArte {versao, em}`. Items that reach checkout without it (old carts, kits, party, facade) get the same checkbox there (order-level `termosArte`). `/api/pedidos` refuses a personalized line without acceptance (`missingTerms`) and the acceptance goes in `desc_trabalho`. Changing the text needs a new `TERMOS_ARTE_VERSAO`; the text is provisional until Padrão validates it.
- Freight is quoted by Padrão's own freight API, which runs Melhor Envio with its account and dispatch CEP; the site never calls Melhor Envio.
  - `src/lib/frete-api.ts` (`server-only`) POSTs `{to:{postal_code}, products:[{id,width,height,length,weight,insurance_value,quantity}]}` to `PADRAO_FRETE_URL` with `x-api-key: PADRAO_FRETE_API_KEY`.
  - Boxes come from the variation's packaging `em` = [kg, width, height, length, lots per box] (the API's `embalagem`); `quantity` = volumes = ⌈lots ÷ lots per box⌉. Pure logic in `src/lib/frete.ts` (tested).
  - Used by the product page "Calcular entrega" (`/api/frete`, an estimate), the main checkout's "Frete por transportadora" (`/api/pedidos/frete` + re-quote at order time) and the multiloja checkout.
  - Local simulator: `scripts/frete-mock.mjs` (port 3197). Never put the real key in tracked files or logs.

The API holds live data. Do not call write endpoints while developing unless the user explicitly asks: `gerarpedido`, `cadastrarcliente`, `atualizacliente`, `atualizarpagamento`, `cancelarcompra`/`cancelarpedido`, `reenviararte`, `recuperar*`, `alterarsenhaatual`.

Dates sent to the API must be DD/MM/AAAA, even though the PDF says AAAA-MM-DD.

### Mockup pipeline (product to 3D)

1. **Registry.** `src/lib/mockup-kinds.ts` defines `MOCKUP_KINDS` and `KIND_INFO`, with default size, scene, dims and art aspect.
2. **Kind and spec.** In `src/lib/mockup.ts`:
   - `resolveKind` tries, in order: slug override (`mockup-overrides.ts`), then the `RULES` regexes on the accent-free name, then `CATEGORY_DEFAULT`.
   - `mockupSpec(product, selection)` builds the `MockupSpec` (measures, colors, variant…) from the name and the chosen options.
3. **Dispatch.** `src/components/mockup/models/index.tsx` maps kinds to models with a `Record<MockupKind, Component>`, so a new kind without a model fails to compile. Models live in family files; a model is built in cm inside a scaled group, front facing +z.
4. **Art.** `src/components/mockup/art.ts` paints the customer's art (image, text and template style) to a canvas. The template picks its layout shape (strip, wide, square, tall, pole) from `ArtRender.aspect`, the logical width ÷ height of the area; pass it whenever you paint (the 3D texture, the 2D editor, style thumbnails, print PDFs and the facade photo do), because the canvas pixel ratio is rounded and a 3:1 sign used to flip between "strip" in 3D and "wide" in the editor. The printable area and layout come from `ArtSettings`, which also carries `layout`, `back`, `mannequin`, `region` and `ledColors` for the web-to-print editor in `src/components/product/art-editor/`.
   - **Sample template and "Em branco".** While the art is empty the style template shows sample text and the Padrão symbol as a "sample logo" (`Scene.exemplo`; with the customer's text Clássico drops the symbol and reflows). On the product page (`ArtStep` `blankOnType`) the first keystroke on an empty surface switches the art to `style: "branco"` (`paintBranco`: only the customer's text on their background, no ornaments); `StylePicker` tiles exclude it (`MODEL_STYLES`) and "Deixar em branco" brings it back. Kits, party, facade and neon don't auto-switch.
   - **Uploaded images go through the automatic handler.** `src/components/mockup/image-intake.ts` decodes with `createImageBitmap` (EXIF orientation) and hands the bitmap to a Worker (`image-intake.worker.ts` → `image-process.ts`, OffscreenCanvas; same steps on the main thread when unsupported), so the page never freezes. SVG is rasterized from its viewBox (vector, no dpi warning; the print SVG keeps the preview's viewBox). A file whose original pixels match the piece's template (sheet/bleed/trim, `madeForTemplate` in `gabarito/jobs.ts`) goes in as is. Otherwise it trims empty margins (measured at 1024 px with a tight tolerance, so thin strokes and light taglines stay), removes a white background on apparel and plastic/kraft bags, and outputs a `blob:` preview (≤ ~4 MP, PNG/JPEG, within the device canvas cap: `canvasLimitsFor`). The print source (original, treated full-resolution PNG, or cropped SVG) and the original `File` ("Usar a imagem original") go to `registerSource`; `retainSources` pins what the page uses and frees swapped images.
   - The pure decisions live in `src/lib/image-prep.ts` (tested): border measured on a 3% band (a thin frame falls back to the inner ring), photo vs logo (transparency, or few colours and little soft shading: `softShading` keeps studio photos on white as photos), focus point, `autoFit` (photo fills the area centred on the subject up to 45% crop; a logo stays whole, centred, capped 2% above the minimum dpi for the piece size, on the colour of its border only when the image is opaque), `dpiTargets` by piece size and texture size.
   - Products without a template are fitted by `src/components/product/auto-fit.ts` (refit when the area changes; "Preencher a área" / "Imagem inteira"; "Voltar ao encaixe automático" in the editor). Template products are fitted by `fitToTemplate` (`gabarito/jobs.ts`), which uses the same analysis for files not made on the template and keeps a mug logo in the front window (`Gabarito.fitWindow`). `templateFit` records the mode, crop, dpi limit and the background the handler set (restored when another image comes in). `plausibleArtwork` (templates.ts) stops a tiny bitmap being matched as final artwork (sheet measured by the sheet, bleed/trim by the piece; vectors always pass). Art textures with an image are 2048 px (1536 on touch devices), 1024 while the 2D editor is being dragged (`art-gesture.ts`).
5. **Viewer.** `MockupViewer.tsx` is loaded lazily, with `ssr: false`, through `Mockup3D.tsx`.
   - Rendering is on demand (`frameloop="demand"`). Floor alignment and framing use the mesh bounds; snapshots feed the cart.
   - Optional room scenes come from `environments/`.
   - Hooks that models can read or set: `userData.view` (initial angle), `userData.noBounds` (exclude from framing), `userData.unitsPerCm` and `roomPose` (room placement), and `useSceneMode()` from `viewer-hooks.ts` (room, back/"Ver verso", motion).

### T-shirt and mannequin

The t-shirt pipeline lives in the folder `src/components/mockup/models/apparel/`. Don't confuse it with the file `models/apparel.tsx`, which holds socks, shorts and swimsuits.
- **`body.ts`:** the parametric display torso. It is a loft of superellipse sections built from girths per body type and size, plus a polar table r(φ, y).
- **`garment.ts`:** dresses that body. The fabric is snug at the shoulders, hangs below the chest and shoulder blades, and turns the extra fabric into ease plus folds. It also defines the neckline and the armhole loop.
- **Other pieces:**
  - `pieces.ts`: sleeves, trims, seams, the print "skin" measured in cm along the fabric, and vertex AO;
  - `polo.ts`: the polo collar;
  - `stitches.ts`: instanced stitching;
  - `textures.ts`: knit normal maps and the armhole alpha mask.
- **`TeeModel.tsx`:** assembles everything. `TshirtModel` in `textile.tsx` routes every variant to it except the baby `body`, which still uses the old panel model.
- **Mannequin setting:** `art.mannequin` holds size and body; `null` hides the mannequin, giving the ghost style. Body measures and fit come from `src/components/product/art-editor/mannequin.ts`.

### Print templates (gabaritos)

- **Data:** `scripts/sync-templates.mjs` → `src/data/templates.json`, using the hand/agent-reviewed overrides in `src/data/template-curation.json` (panels referenced by cut centre `at`). Only the server reads the JSON (`src/lib/templates-data.ts`, `server-only`); the product page gets the product's own sheets as `printTemplate`.
- **Logic:** `src/lib/templates.ts` is pure and test-importable: picking sheets for the selection (`pagesFor`, an option value mapped to no sheet means no template), pieces and faces (`piecesOf`, `panelFor`), orientation (`orientPages`), artwork matching and fit (`matchArtwork`, `autoPlacement`), mm↔editor placement.
- **UI:** `ArtEditor2D` takes `template` (the piece's upright panel): the stage is the cut, the canvas includes the bleed (`paintArt(..., { bleed })`, which also stretches the edge pixels into the bleed), and the image may overflow (`ArtLayout.overflow`). `src/components/product/gabarito/` has the "Gabarito oficial" block, the SVG sheet, the PDF builder (`pdf-lib`, lazy) and the PDF reader (`pdfjs-dist`, lazy).
- **Files:** the print PDF is stored in IndexedDB (`print-store.ts`); cart lines keep only `printFile.id`.

### Product page, cart, extra flows

- **Product page.** `src/components/product/ProductExperience.tsx` turns option selection into a variation and a quote (`src/lib/pricing.ts`: tiers, m² area pricing, express, size grid). It also builds the spec and the `ArtStep`, and adds to the cart with a snapshot. Since Padrão's review of 2026-10-25 ("Observações Site Novo"): a variation without personalization (plain product, ready-made neon) shows only the photos (no 3D tab, no "Pré-visualizar", no "Mockup 3D grátis" badge); the main store has no PIX discount and no "Enviar arte depois" (`/api/pedidos` refuses a line without art via `missingArt`). Multiloja stores keep both, through the `pix` and `allowArtLater` props (`ProductExperience`, `ArtStep`'s optional `onArtLater`, `CartDrawer`/`CartPageView` `pix`). Also from that review: the template download sits under the viewer, highlighted; fixed product notices live in `src/lib/avisos-produto.ts` ("Caixa de luz não inclusa" on 241/334); "Enviar sua arte" opens the "Selecione a arte" modal (`SendArtDialog.tsx`, request of 2026-10-25).
  - **Production files first:** the single file ("Arquivo Único", always offered, `anexosDeProducao`) or one file per API attachment type, each hiding the other (`camposVisiveis`). Building the art on the site from an image comes last, and only while no production file was sent.
  - **Front covered** (`frenteEnviada`: single file or "Impressão Frente"): the files go to production as sent, with no editor PDF. The art step shows only `ProductionSummary`; the files still feed the 3D preview (front and back).
  - **Highlight:** the modal shows the art on the product, a transparent capture of the page 3D (`snapMockup`), when the file can be read; otherwise a thumbnail.
  - **Art name and note** go into the order (`nome_trabalho` and `descricao`).
  - **Art creation by Padrão** (`Customizacao.criacao`, `criacaoPorVariacao`): the cart item gets `criacaoArte`. `priceLine` charges the catalog price once per item (`PricedLine.criacao`), and the order sends `arte.tipo` 2 (assumption) with `arte.preco`. The customer's request goes in the options, the references as attachments. m² pricing: `areaRules`/`areaQuote` (1 m² minimum per item, per-variation limits `lm`, fixed-price `a: 0`) and the LED neon rules (`Product.neon`, `NEON_FRASE`, `NeonSizeStep`, `neonTextBox`): see README "Preço por m²".
- **Art base (same review; README "Arte: superfícies, verso, processos e arquivos automáticos").** All rule modules are pure and tested.
  - **Surfaces** (`src/lib/superficies.ts`): front = `art`, back = `art.back`, other parts = `art.faces[id]`, taken from the template's `other` pieces. Varnish-mask sheets (`folhaDeVerniz` in templates.ts, read from the `part` field) are never surfaces and never go in the print PDF.
  - **Sublimated apparel** (`spec.fullPrint`):
    - which products: shirts, abadás, vests, tank tops, pajamas and the shorts;
    - the 3D: the fabric takes the art's background colour; the art covers each surface edge to edge (front and back skins and each sleeve in `TeeModel`, 4 leg parts in the shorts);
    - trims: the finish's viés or ribana colour (`accentColor`).
  - **Polo:** the back uses the option's back area (`backPrintCm`).
  - **Pet bed:** every surface comes from its template: seat, base, and the walls inside and out (no separate back).
  - **Processes** (`src/lib/processo.ts`): P&B, laser, wood carving and DTF, applied through `ArtSettings.mono` at the end of `paintArt`.
  - **Orientation** (`src/lib/orientacao.ts`): the crachá, the canvas and fixed-size banners can be horizontal or vertical.
  - **Automatic contour** (`src/lib/contorno.ts`, `spec.contour`):
    - lona 41: the 3D sheet is cut out and the order gets a "Faca de Corte" PDF;
    - LED frame 337: LED lines (`src/lib/led-linhas.ts`, tested, front only, `ArtSettings.led`). The LED strip lights one color per continuous line: each auto-contour loop (one per island of the drawing, colors kept by loop order, largest first) and each brush line has its own color; to change color the customer finishes the line and starts another. The editor (`ArtEditor2D` `led` prop, `LedLinesPanel`, `use-led-contour.ts`) shows the lit lines over the UV print on a dark wall and, with the brush on, a drag draws (a later stroke continues the line in progress; a click goes straight there; double-click or "Finalizar linha" ends it, closing it when it ends near the start). Finishing a line interprets the hand-drawn stroke and redraws it clean (`src/lib/led-forma.ts`, tested: straight line, rectangle, circle/ellipse, polygon or smoothed free stroke, corners at `LED_RAIO_CM` = 2 cm, provisional); the stroke as drawn stays in `LedLinha.original` ("Usar o traço como desenhei" / "Corrigir este traço"), and `LedDesenho.corrigir = false` turns it off. An uploaded image on white loses the white background so the contour follows the drawing; a photo/opaque art gets the frame loop. The 3D (`NeonFrame`) and the "Posição do Led" PDF (page 1 magenta lines, page 2 lines in their LED colors with numbers and a legend; `arquivoDeLed`) use the same `linhasDeLed`, and the cart line gets "Linhas de LED".
  - **Spot varnish** (`src/lib/verniz.ts`):
    - the customer picks the varnished layers in `ArtSettings.varnish`;
    - `varnishMask` paints the mask, sent as the "Verniz Local Frente/Verso" or "Verniz Localizado" attachment and reused as the 3D clearcoat map.
  - **Customer files win:** the automatic files are made at add-to-cart only when the customer sent neither their own file nor the single file.
- **Cart.** `src/components/cart/CartProvider.tsx` stores the cart in localStorage.
- **Crie Sua Festa / Monte Seu Kit:** `src/lib/party.ts` and `components/party/`. The custom kit builder (`/monte-seu-kit/montar`, `components/kit/`) is a 4-question assistant (goal, number of kits, budget per kit, must-haves) over curated catalog products (`KIT_PRODUCTS`/`KIT_GOALS` in `src/lib/kit-builder.ts`, pure and tested) plus catalog search (`/produtos/indice.json` + `/api/kit/produto`). `planKitItem` prices each item for the whole order (units per kit × kits) in the right tier (variation `mn`/`mx` or tier products), the cheapest lot (stickers, menus) and the product minimum, reusing `priceItem` with a 999 ceiling; items go to the cart with `cartLines` and a kit `bundle`. Personalization (`components/kit/kit-art.ts`): one logo/name/style/palette for the whole kit (`kitBaseArt`), fitted to each item's print area (`sharedItemArt` → `autoFitArt`, white removed on apparel), per-item overrides from `KitArtEditor` (the product `ArtStep` + 3D in a dialog; `step` is optional there), no "send later" (removed on 2026-10-25 at Padrão's request: every item needs art), and 3D photos per item keyed by `photoKey` (taken by `KitPreview` when the model settles and by `KitGallery`, one viewer at a time). Keep a single WebGL canvas on screen: the aside preview pauses while the editor or the gallery is open.
- **Quantity tiers:** 44 products have a tier option ("De 1 até 10", "De 11 até 100"…) with per-row limits in the API. Variations keep their own range as `mn`/`mx` (catalog-map `variationLimits`); always read limits with `unitLimits(product, variation)` (pricing.ts) — the product page, the cart (`/api/precos/limites` returns per-variation ranges) and `priceLine` do.
- **Fachadas:** `src/lib/facade.ts` and `components/facade/`. `FacadeStudio` uses the product `ArtStep` editor (family `sign`) for the sign art (typed or uploaded) and shows it on the `storefront` 3D mockup (`models/storefront.tsx`, built in cm around the sign size from `sceneSpec`) or, optionally, in perspective on the customer's shop photo (the same art painted to a canvas). `storefront` is a page-only kind (`PAGE_KINDS` in `mockup-kinds.ts`, exempt from the "every kind has a product" test); `KIND_INFO.orbit` keeps it front-facing (no auto-spin, limited orbit), `userData.view.distance` frames it closer, and `userData.noFrame` keeps the interior seen through the glass out of the framing but in snapshots. Clicking a style (`ArtStep.onStylePick`) bumps the viewer's `focus` prop: the camera tweens front-on to the `userData.focus` group (sign + spotlights), the studio dims to dusk (`StudioLights` `dusk`, `duskBackdrop`) and the model lights its spotlights from `useSceneMode().focus` (sign `lightMapIntensity`, lens emissive, additive halo/beam/spill, updated per frame without re-rendering).

### Site images and banners (admin → Site)

- **What it does.** The Padrão admin (`/admin/site/imagens`, `/admin/site/banners`) can:
  - replace product photos (the first is the card cover) and category images/banners, even when the API sends others;
  - manage the home page banners: the top carousel and the promo strips after "Mais vendidos", grouped by `linha`. With every carousel banner switched off, the home shows no carousel.
- **Default images (Figma).** `src/lib/midia-padrao.ts` (`MIDIA_PADRAO`, pure, tested) holds the Figma photos in `public/site/`: product photos by catalog id (`produtos/<id>.webp`, 600×804 studio grey, re-encoded from the Figma originals at WebP q95), the 5 round category photos (`categorias/<slug>.webp`, 800×800), the 5 top banners (2560×800 + 2160×2700 mobile) and the wide "Cartões de visita e postais" strip. Banners, categories and the orange outline mark were upscaled 2× from the Figma files with Real-ESRGAN x4plus (ONNX on the GPU, outside the repo); product photos were not, because it smooths fabric/paper and invents tiny text. `next.config.ts` serves AVIF first, with qualities 75 (default) and 90 (banners, `BannerImagem`). `comPadrao` (midia.ts) lays what the admin saved on top: products per id, categories field by field, banners by place when a list is saved. `midiaDoSite()` returns the merge (only the defaults without a DB); `midiaAtual()` stays raw so the admin knows what is its own. Deleting a saved record brings the default back; to show no banners, switch each one off. `imagemPermitida` accepts `/site/(produtos|categorias|banners|marca)/…` and `/produtos-novos/…`. The order payload still uses the catalog image (`productFacts`), never these.
- **Code.**
  - `src/lib/midia.ts` is pure and tested: apply to the catalog, validate admin input, schedule, strip rows, image size from the file header.
  - `src/lib/midia-servidor.ts` holds the DB and cache: table `site_midia` (migration 4), keys `produto/<catalog id>`, `categoria/<slug>`, `banners/<lugar>`.
  - Files live in `arquivos` with owner "site" and are served by `/api/site/imagem/<nome>`.
  - Server Actions are in `app/(admin)/admin/site-actions.ts`, the editors in `components/admin/site/`, the store banners in `components/home/{BannerCarousel,PromoBanners,BannerImagem}.tsx`.
- **Product key.** Products are keyed by the catalog `id`, not `groupId`: the derived "tags" product shares group 180.
- **Rendering.** Store pages stay SSG and read the overrides with `await midiaDoSite()` (`unstable_cache`, tag `site-midia`). Saving calls `updateTag`, and each page regenerates on its next request (verified with `next build` + `next start`).
  - The cache key is random per process, so a build never reuses `.next/cache` data from another run.
  - During `next build` the pool uses one connection per worker and failed reads retry.
  - Without a DB the pages fall back to the default images (and API images where there is no default).
- **Where overrides apply.** Any new page or route that shows catalog images must map them through `produtosComMidia` / `categoriasComMidia`, as home, category, products, product, layout menu, search index, party, kit, business, templates and the multiloja `lojaItens`/`vitrineDados` do.

### Multiloja (stores for influencers and suppliers)

- One install serves every store by host: `src/proxy.ts` rewrites `<sub>.<MULTILOJA_DOMINIO>` (dev: `<sub>.localhost:3100`) to `src/app/(vitrine)/vitrine/[host]/`; `/api` and `/painel` are never rewritten. The store's palette overrides the coral CSS variables (`paletteVars`).
- Lojista panel: `src/app/(painel)/painel/` (Server Actions in `actions.ts`; the store always comes from the session via `requirePainel()`). Padrão admin: `src/app/(admin)/admin/` (`requireAdmin()`).
- `src/lib/multiloja/`: `core.ts` and `pedido.ts` are pure and tested (host parsing, margin/price, plans, palettes, order totals, commission, balance); `pg.ts` (PostgreSQL pool, `?` placeholders, migrations; no `server-only`, the scripts import it too), `schema.ts` (migrations), `db.ts` (server pool, migrates on first use), `repo.ts` + `repo-vendas.ts` (all SQL), `auth.ts` (scrypt + sealed cookies for lojista and admin), `tenant.ts` (store from host, priced products), `vendas.ts` (place order, confirm payment, send to production), `payments.ts` (gateway dispatcher over `gateways/{efi,cielo,simulado}.ts`), `config.ts` (settings saved in the DB first, then env), `settings.ts` (`configuracoes` table; secrets sealed), `files.ts` (uploads and order art, stored in the `arquivos` table), `analytics.ts` + `eventos.ts` (tracking).
- Orders: the server reprices every cart line with `priceLine` at store price and at base price; the browser total is only compared (409 when it changed). Payment webhooks are re-checked against the provider before marking "pago".
- Store design: `/painel/personalizar` edits a theme (`src/lib/multiloja/tema.ts`, pure and tested: models, ready sections, `parseTema` validation). Draft in `lojas.tema_rascunho`, published in `lojas.tema`. `components/vitrine/loja/Secoes.tsx` renders the home sections for both the live store (server) and the editor preview (`/painel/previa` in an iframe, updated by `postMessage`), so it must stay free of server-only imports: all data comes in `VitrineDados` (`lib/multiloja/vitrine.ts`). Theme CSS: `loja/estilo.ts` (variables + `data-*`) and the unlayered `.loja-tema` rules at the end of `globals.css`.
- Shipping: `cotarFrete` (`vendas.ts`) quotes through Padrão's freight API (see Data flow), one product per cart line from the variation's packaging. Without `PADRAO_FRETE_API_KEY`, each store's fixed freight applies. A product without packaging blocks online checkout (WhatsApp). `placeOrder` re-quotes and stores `frete_servico`/`frete_custo`/`frete_prazo`.
- Production send (`gerarpedido`) only with `PADRAO_ORDERS_ENABLED=true` and `PADRAO_MULTILOJA_CLIENTE_ID`; otherwise simulated.
- Payments: Pix, boleto and card, each with its own gateway. In `/admin/pagamentos` the admin picks the gateway per method (Efí, Cielo, Pagar.me, simulado or off), e.g. Pix via Pagar.me and card via Cielo; "Usar para tudo" puts one gateway on every method it supports. Pure routing rules live in `pagamento-rotas.ts` (tested); the old single-gateway setting (`ativo` + `metodos`) is read as per-method routes. Each order stores `pagamento_provedor`, so status checks, notices, refunds and voids always go to the gateway that created the charge. A gateway implements the `Gateway` interface in `gateways/types.ts`.
- Efí (Pix API + Cobranças API) and Cielo (API E-commerce 3.0 for Pix/boleto + Link de Pagamento for card): routes checked against the official docs; tested end to end against the local simulators `scripts/efi-mock.mjs` and `scripts/cielo-mock.mjs` (set `MULTILOJA_EFI_MOCK_URL` / `MULTILOJA_CIELO_MOCK_URL` in `.env.development.local`, never in production). Neither has run against the real sandbox yet.
- Pagar.me (API v5, Pix only): `gateways/pagarme.ts` with pure payload/status/webhook parsing in `gateways/pagarme-dados.ts` (tested). The stored charge id is `ch_…`; webhooks hit `/api/multiloja/pagamento/pagarme` with `?hmac=` (or the secret as the Basic auth password) and only trigger `GET /charges/{id}`; `DELETE /charges/{id}` voids an open Pix or refunds a paid one. Local simulator: `scripts/pagarme-mock.mjs` (port 3195, `MULTILOJA_PAGARME_MOCK_URL`).
- Tracking: the main site (loja 0) and the stores send anonymous events to `/api/eventos` (`src/lib/tracking.ts`, `PageTracker`); the server records orders created/paid. Funnel figures count distinct sessions. Respect GPC/DNT; never store names, e-mails or IPs in `eventos`.
- Everything multiloja lives in PostgreSQL (`DATABASE_URL` in production; `npm run dev` runs a local one). Every data function is async: always `await` it, including in conditions (`if (!(await signupOpen()))`); TypeScript does not flag `!promise`. Dates are UTC text from `agora()`; money is double precision; yes/no columns are 0/1 integers.
- A new migration in `schema.ts` needs a dev-server restart (the pool and the migration run are cached on `globalThis`).
- `npm run multiloja:seed` recreates the demo store `atelie-demo` and a test admin (test logins inside the script).
- Server components must not call `Date.now()`/`new Date()` directly (React Compiler purity rule): use `sqlDaysAgo`, `dayKeyDaysAgo`, `commissionReleased` from `core.ts`.
